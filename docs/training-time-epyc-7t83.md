## 单步耗时分解 (EPYC Zen 3 核心, 单线程)

以下测算基于：纯 CPU PyTorch (oneDNN/MKL 后端), numpy 矢量化操作, Python 3.x,
Zen 3 核心 ~3.5GHz 单核加速, 22×10 棋盘完全在 L1 缓存内。

```
一次 env.step() + agent.select_action() 的细分:
┌──────────────────────────────┬──────────────┬─────────────────────────┐
│ 操作                         │ 估算耗时(us) │ 说明                    │
├──────────────────────────────┼──────────────┼─────────────────────────┤
│ get_legal_actions()          │  150 - 300   │ ~56-112 位置 × 碰撞检测 │
│                              │              │ + ghostY while 循环     │
│ StateEncoder.encode()        │   50 - 150   │ 棋盘遍历 + one-hot 构建 │
│ PyTorch forward (B=1, CPU)   │  150 - 400   │ 3×Conv2d + 7×Linear     │
│                              │              │ Python↔C++ dispatch 占半 │
│ env.step() 执行              │  100 - 250   │ 放置+消行+特征+生成     │
│ Action mask + argmax         │    5 - 15    │ 布尔掩码 + 最大值索引   │
│ agent.observe()              │   20 - 50    │ N-step buffer + 记忆插入 │
├──────────────────────────────┼──────────────┼─────────────────────────┤
│ 单 env 单 step 合计          │  475 - 1165  │ 中位数 ≈ 750 us         │
└──────────────────────────────┴──────────────┴─────────────────────────┘
```

## DQN (Rainbow) 训练总时间

### 环境采集阶段

```
每训练迭代 (64 envs 串行 for 循环):
  单 env step:  ~750 us
  64 envs:      ~48 ms/iter

  总迭代数: 50,000,000 / 64 = 781,250 次
  采集总时间: 781,250 × 48ms = 37,500s ≈ 10.4 小时
```

### DQN 训练更新阶段

```
DQN update (每 4 步触发一次, batch_size=32):
  记忆采样 (SumTree):     ~1.0 ms  (CPU numpy)
  CPU→GPU 传输:           N/A (纯 CPU)
  Forward ×3 (B=32):      ~2.0 ms  (一次 online, 两次 no_grad)
  Loss + backward:        ~4.0 ms
  Optimizer.step():       ~1.0 ms
  优先级更新:             ~1.0 ms
  每次更新合计:           ~9.0 ms
  每迭代摊销: 9.0 / 4 =  ~2.3 ms/iter

  更新总时间: 781,250 × 2.3ms = 1,797s ≈ 0.5 小时
```

### 预训练阶段 (一次性)

```
专家数据收集 (Dellacherie):
  1000 局, 每局 ~347 步 = 347,000 transitions
  每步包括 get_legal_actions + expert.select_action + env.step
  耗时: ~347,000 × 400us ≈ 139s ≈ 2.3 分钟

行为克隆训练 (BC):
  347,000 样本, batch_size=256, 50 epochs
  每 epoch: ~1,356 次 forward+backward (B=256)
  单次 (B=256, CPU): forward ~3ms + backward ~8ms ≈ 11ms
  总更新: 50 × 1,356 × 11ms ≈ 746s ≈ 12.4 分钟
  预训练合计: ≈ 15 分钟
```

### 评估开销

```
每 10,000 步评估 100 局:
  评估次数: 50M / 10K = 5,000 次
  每次评估: 100 局 × ~500 步/局 × ~800us/步 ≈ 40s
  评估总时间: 5,000 × 40s ≈ 55.6 小时 ← 占比过高!

  注: 此处评估频率过高会导致评估时间远超训练时间。
  实际建议: eval_every >= 50,000 或减少 eval_episodes。
  以下按 eval_every=10,000 计算（默认值），但标注此问题。
```

### DQN 总时间汇总

```
┌────────────────────┬──────────────┬──────────┐
│ 阶段               │ 估算时间     │ 占比     │
├────────────────────┼──────────────┼──────────┤
│ 环境采集           │ 10.4 小时    │ 15.6%    │
│ DQN 训练更新       │  0.5 小时    │  0.8%    │
│ 预训练 (一次性)    │  0.25 小时   │  0.4%    │
│ 评估 (eval)        │ 55.6 小时    │ 83.3%    │
├────────────────────┼──────────────┼──────────┤
│ DQN 合计           │ ≈ 66.7 小时  │ 100%     │
│ (排除评估后)       │ ≈ 11.2 小时  │          │
└────────────────────┴──────────────┴──────────┘
```

> **重要发现**: 默认 `eval_every=10,000` 导致评估占比 83%，严重拖慢训练。
> 排除评估后的纯训练时间为 **≈ 11 小时**。

## 瓶颈分析

### 时间分布 (排除评估, DQN)

```
get_legal_actions():  ████████████████████████████████  48%
PyTorch forward:      ████████████████                  24%
env.step():           ██████████████                    20%
其他:                 ████                               8%
```

### 核心瓶颈

1. **get_legal_actions() 占近一半时间**: 纯 Python 循环 + numpy 访问, 每次 ~56-112 次碰撞检测
2. **PyTorch B=1 forward 开销**: Python↔C++ dispatch 开销 > 实际计算开销
3. **串行 env 处理**: 64 个环境在单个 Python for 循环中串行执行, GIL 阻止多核利用
4. **评估开销**: 默认 eval_every=10,000 导致评估时间远超训练时间

### EPYC 7T83 的特殊优势

- **256MB L3 缓存**: 22×10 棋盘 + 所有 tetromino 形状完全在 L1/L2 缓存内, 缓存未命中率接近 0
- **Zen 3 高 IPC**: Python 的分支密集型代码受益于 Zen 3 的 8-wide 发射和 µop 缓存
- **8 通道 DDR4-3200**: ~200 GB/s 内存带宽, 远超需求

### EPYC 7T83 的劣势

- **单核频率偏低** (3.5GHz max): 相比桌面 CPU (5GHz+), Python 串行代码性能受限
- **128 线程无法利用**: GIL + 串行 for 循环 = 仅 1 个核心工作
- **跨 CCD 延迟**: 如果 PyTorch MKL 尝试多线程但跨越多个 CCD (8 个 CCD, NUMA), 可能产生反向加速

---

## 推荐的 MKL/OpenMP 配置

训练前设置以下环境变量以避免多线程争用:

```bash
# 限制 MKL 线程 (小模型多线程反而慢)
export OMP_NUM_THREADS=4
export MKL_NUM_THREADS=4

# 或者完全禁用 MKL 多线程 (对于 B=1 推理最优)
export OMP_NUM_THREADS=1
export MKL_NUM_THREADS=1

# NUMA 绑定到单个 CCD (32MB L3)
numactl --cpunodebind=0 --membind=0 python scripts/train.py --device cpu --envs 64
```

## 总结

| 算法 | 默认配置 (含评估) | 排除评估 | eval_every=50,000 优化后 |
|------|-------------------|----------|--------------------------|
| DQN (Rainbow) | ~67 小时 | **~11 小时** | **~16.5 小时** |
| PPO | ~69 小时 | **~14 小时** | **~19 小时** |

### 关键结论

1. **纯训练约 11-14 小时** (排除评估开销)
2. **默认评估频率 (10,000) 过高**, 导致评估占 80%+ 时间
3. **get_legal_actions() 是最大瓶颈** (48% 时间), 通过 C++ pybind11 可降为 1/5
4. **PPO 比 DQN 多约 3 小时**: PPO 更新计算量大但次数少, DQN 更新轻但频繁
5. 建议将 `eval_every` 设为 50,000~100,000, `eval_episodes` 降至 20~50
